# BL-0007: In-Memory Module Execution for Debugging

## Why
- Debugging module code currently involves separate worker processes. An in-process option would let developers debug the host and selected modules in one process.

## What
- Add an opt-in, per-module in-memory execution mode. A host can run in-process and isolated modules together.
- Run each selected in-process module inside the host, without a separate worker process or OS service registration for that module.
- Preserve the observable behavior of existing public routes and typed clients in both modes. In-process communication must not use a loopback network.
- Keep existing isolated execution as the default. Preserve existing host OS-service support.
- Start and stop in-process modules with the host and report their status accurately. Do not represent them as independently supervised worker processes.
- In-process modules share the host process. They do not have OS-level worker isolation or independent worker restart guarantees. Use normal host-process failure behavior.
- Dependencies: No additional backlog item identified.

## Current state
- [`WorkerManager`](../../src/ModularMonolith.Host/WorkerManager.cs) allocates endpoints, starts registered worker processes, waits for readiness, supervises them, and reports worker status.
- [`IWorkerTransport`](../../src/ModularMonolith.Platform/Transport/IWorkerTransport.cs) defines endpoint allocation, HTTP client handlers, Kestrel binding, and cleanup. [`WorkerTransports`](../../src/ModularMonolith.Platform/Transport/WorkerTransports.cs) selects Unix sockets or named pipes by default.
- [`WorkerForwarderHttpClientFactory`](../../src/ModularMonolith.Host/WorkerForwarderHttpClientFactory.cs) uses a `SocketsHttpHandler` connection callback for proxy traffic. A new transport alone may not support in-process routing.
- The [local development instructions](../../README.md#running-locally-development-mode) run the host directly, but it still starts child workers.

## How
- Design per-module execution selection and in-process module hosting. Reuse existing module declarations and behavior where practical.
- Determine how public proxy routes and typed clients reach in-process modules without loopback networking. Changes may be needed beyond `IWorkerTransport`; the mechanism is an open design decision.
- Integrate lifecycle, readiness, shutdown, and status for both modes without claiming process isolation for in-process modules.
- Document configuration, debugging steps, and the differences in isolation, failure handling, and restart behavior.

## Verification and acceptance
- [ ] With no new configuration, existing isolated modules still launch as worker processes and retain their existing behavior.
- [ ] Selecting in-process mode for a module runs it in the host process without launching a worker process or registering a separate OS service. Its in-process communication does not use a loopback network.
- [ ] A mixed configuration runs selected modules in-process and other modules as isolated workers. Both are reachable through their existing public routes and typed clients.
- [ ] Automated tests compare representative successful and failing public-route and typed-client behavior across both modes, including request context and cancellation where applicable.
- [ ] Automated tests verify module startup, shutdown, readiness, and truthful status for in-process and isolated modules, including mixed mode. In-process status does not claim independent worker supervision or restart.
- [ ] Existing isolated transport, routing, and worker lifecycle tests pass. Document how to select the mode and debug modules, including its isolation and failure limitations.
