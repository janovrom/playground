# BL-0005: Circuit Breaking, Poison-Pill Quarantine & Dead-Letter Handling

## Why
- A payload that repeatedly crashes a worker can lead to a crash loop.

## What
  1. **Sliding-Window Circuit Breaker**: If a module worker process crashes $M$ times within rolling window $T$ (e.g. 3 crashes in 2 minutes), transition the module state to `Open` (suspended) and fail fast with HTTP 503.
  2. **Poison-Pill Quarantine**: Compute a SHA-256 hash of incoming request payloads. If a payload correlates with 2 consecutive worker crashes, quarantine the payload to dead-letter storage and return HTTP 422 (`PoisonPillException`).

- Dependencies: BL-0001, BL-0002.

## Current state
- The existing backlog describes this state; it has not been reverified during this migration: If a malicious or malformed payload triggers an unhandled crash or OOM in a worker, `WorkerManager` restarts the worker and re-attempts requests, potentially entering an infinite crash loop until systemd or Windows service failure limits trip.

## How
1. **Crash Correlation**: `WorkerManager` records crash timestamps and active request hashes in a thread-safe ring buffer.
2. **Operator Reset**: Expose `POST /modules/{name}/reset` to manually clear the circuit breaker after resolving underlying faults.

## Verification and acceptance
- Verify crash handling and quarantine with the tests below. Open question: define tests for payload correlation, HTTP responses, and operator reset.
- [ ] A test simulating consecutive worker crashes trips the circuit breaker and stops process spawning.
- [ ] Poisoned requests are quarantined and subsequent valid requests to other routes proceed unaffected.
