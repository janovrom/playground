# BL-0004: Unified Packaging Pipeline & Single Distribution Bundle

## Why
- Adding a module currently requires editing hardcoded Host packaging targets.

## What
- An automated MSBuild packaging workflow that dynamically batches all referenced worker projects into the `workers/` distribution directory, supporting both framework-dependent and self-contained publications.
- Dependencies: BL-0003.

## Current state
- The existing backlog describes this state; it has not been reverified during this migration: `ModularMonolith.Host.csproj` has hardcoded MSBuild targets (`CopyWorkerOutputs` and `CopyPublishedWorkerOutputs`) with static references to `ModularMonolith.Worker.SvgRenderer` and `ModularMonolith.Worker.ImageCache`. Adding a module requires editing the Host csproj.

## How
1. **Dynamic MSBuild Batching**: Replace hardcoded targets with an item group (e.g., `<WorkerProject Include="..." />`) that executes `Publish` or `Build` across all modules.
2. **Distribution Layout**: Produce a unified output directory containing:
   ```
   ModularMonolith.Host (.exe / ELF)
   appsettings.json
   appsettings.linux.json / appsettings.windows.json
   workers/
     ModularMonolith.Worker.SvgRenderer/
     ModularMonolith.Worker.ImageCache/
   ```
3. **Deployment Script Compatibility**: Ensure outputs match expectations of `deploy/scripts/install.sh` and `deploy/windows/install.ps1`.

## Verification and acceptance
- Verify publication and module changes as described below. Open question: define checks for both publication modes and deployment-script compatibility.
- [ ] Running `dotnet publish ModularMonolith.Host -c Release` packages all workers into `workers/<ProjectName>` automatically.
- [ ] Removing or adding a module project reference updates the published bundle without manual target edits.
